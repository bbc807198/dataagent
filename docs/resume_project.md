# 简历项目说明：DataAgent（AI 数据分析 Agent）

> 本文用于求职材料。所有描述均对应**仓库内可验证的源码与测试结果**；
> 未验证的能力（真实模型效果、生产性能）明确标注为未验证。

## 1. 一句话介绍

基于 LLM 的**受约束数据分析 Agent**：把自然语言问题编译成结构化分析计划，在封闭指标目录上生成参数化 SQL，经 AST 安全校验后只读执行，再用 Python 做确定性统计，输出带证据 ID 的中文报告——让"AI 做分析"这件事**可审计、可复现、不编数字**。

## 2. 简历精简版（3–5 条，可直接粘贴）

- 独立设计并实现 **LLM + 受约束执行器**架构：LLM 只输出 Pydantic 白名单计划，SQL 由确定性模板编译（参数绑定），从架构上杜绝"模型自由写 SQL"的注入与越权风险。
- 实现 **SQLGlot AST 级安全校验器**：表白名单、只读单条 SELECT、禁 `SELECT *`/外部文件访问、用户级数据保护（`user_id` 仅允许聚合计数）、列-表静态绑定，并配套只读执行器（行数上限、超时取消、审计）。
- 构建**证据化报告**：14 节 Markdown + JSON 证据（`[E00x]` 双向对应），结论携带查询名/单位/实际窗口/公式/警告；LLM 叙述层受证据约束，四类失败（截断/完整性/证据/API）明确回退。
- 建立**可复现评测体系**：50 道固定问题（35 有效 + 15 负面）+ 独立核算标准答案（DuckDB 独立 SQL + Python 算术复算，可检测篡改），输出执行成功率/答案正确率/正确拒绝率与 P50/P95。
- 交付**双入口作品**：命令行 + 本地 Streamlit 界面（默认 Mock + 合成数据，无需 Key 即可演示，含 8 个内置演示场景与预期结果标注），并附架构/使用/评测/验收/简历五份文档与 CI 工作流。

## 3. 技术亮点

| 亮点 | 具体做法 |
|---|---|
| 计划即契约 | `AnalysisPlan` Pydantic Schema，`extra="forbid"`，指标/维度/操作/期限全白名单，含 SQL 字段直接被拒 |
| SQL 不由模型写 | `query_builder.py` 是封闭目录上的**确定性编译器**：固定模板 + `?` 参数绑定；用户输入永不进 SQL 语法 |
| 双层安全 | AST 校验（`sql_guard`）+ 连接层限制（只读、`enable_external_access=false`、扩展自动加载关闭） |
| 失败关闭 | 澄清/计划拒绝/SQL 拒绝/超时/数据不足/口径不匹配均为显式状态，不生成"成功"报告 |
| 证据可追溯 | 每条结论 ↔ `.evidence.json` 条目；数值全部来自 Python 统计，不让模型口算 |
| 评测可信 | 标准答案独立核算（不复用被测代码）；可验证分母**事前固定**；离线/真实评测严格区分 |

## 4. 核心架构设计理由

```
自然语言 → IntentParser（LLM，仅产出计划）
        → QueryBuilder（确定性编译，参数绑定）
        → SQLGuard（AST 白名单校验）
        → QueryService（只读执行 + 限额 + 审计）
        → Analytics（Python 统计 + 证据）
        → ReportGenerator（Markdown + JSON；可选 LLM 叙述）
```

**为什么不让 LLM 直接写 SQL？**

1. **权限不可控**：模型可以写出任意 JOIN/子查询/函数，白名单难以穷举；
2. **口径会漂移**：同一问题两次运行可能口径不同，报告不可复核；
3. **数字不可信**：模型倾向"编造合理数字"，而业务分析要求逐条可追溯；
4. **无法审计**：自由 SQL 难以做静态检查与回归测试。

本项目的取舍是：**用 LLM 处理"理解"，用确定性代码处理"执行与计算"**。
代价是覆盖面有限（只支持 9 个指标、7 类分析），收益是可审计与可回归。

## 5. SQL 安全与数据可信度设计

| 层 | 机制 |
|---|---|
| 计划 | 指标/维度/操作白名单；类别字段仅 `eq/ne/in`；期限白名单；筛选值形状校验 |
| 生成 | 模板 + 参数绑定；仅两类已审核 JOIN；生成期先过一遍 `sql_guard` |
| 校验 | 单条只读 SELECT、表白名单、函数白名单、禁 `SELECT *`、`user_id` 仅聚合、用户级金额列仅聚合、维度列必须 GROUP BY、集合聚合拒绝、列-表绑定 |
| 执行 | 只读连接、外部访问关闭、行数上限（1000/硬上限 10000）、超时取消、并发串行化、审计不含参数值 |
| 统计 | 指标完整性（缺失/多口径 → `incompatible_metric`）、零基数不输出无穷大、缺失不补零、缺组不视为 0 |
| 报告 | 证据 ID 双向对应、模式标识（Mock/合成 ≠ 真实）、复现元数据（不含密钥） |

## 6. Benchmark 指标及局限

| 指标 | 定义 | 当前结果（离线） |
|---|---|---|
| 执行成功率 | SQL 与统计都成功的有效案例 / 35 | **100%**（35/35） |
| 答案正确率 | 数值/日期/指标/口径全部符合容差 / 可验证案例（分母事前固定） | **100%**（35/35） |
| 行为正确率 | 行为类别符合预期 / 全部 50 例 | **100%**（50/50） |
| 正确拒绝率 | 负面案例被正确拒绝/澄清 / 15 | **100%**（15/15） |
| 响应时间 | 端到端 `perf_counter` | P50 ≈ 96 ms / P95 ≈ 182 ms（合成数据，非生产性能） |

**局限（必须说明）**：

- 离线评测使用**注入计划**，衡量的是执行链路，**不代表真实模型的自然语言理解准确率**；
- 测试集仅 50 例、合成数据 12 行，指标波动大；
- 真实模型评测需 API Key（本环境未执行），成本无价格表时为 `N/A`；
- 无 k-匿名抑制，细粒度统计存在披露风险。

## 7. 典型技术难点与解决

| 难点 | 现象 | 解决 |
|---|---|---|
| 模型输出不合规 | 缺字段/多余字段/含 SQL | Schema `extra="forbid"` + 一次受控修复重试；评测中关闭重试以控制费用 |
| 分组被静默忽略 | 趋势分析丢失 `group_by` | 趋势分支显式把全部维度进 SELECT/GROUP BY，并加回归测试 |
| 指标口径混淆 | 同指标多个聚合列 | 按 `(metric_id, term)` 精确映射，缺失/多列一律拒绝 |
| 极值口径矛盾 | 报告同时出现 -33% 与 -100% "降幅最大" | 拆成三类极值（最大降幅/涨幅/绝对波动）分别计算 |
| LLM 叙述截断 | 摘要半句结束 | `finish_reason=length` + 完整性校验（悬空连接词/引号配对/句末标点）→ 回退确定性文本 |
| 评测自证 | 用被测代码生成标准答案 | 独立 SQL + Python 算术复算 + 篡改检测测试 |

## 8. 与普通 Text-to-SQL Demo 的区别

| 维度 | 常见 Text-to-SQL Demo | 本项目 |
|---|---|---|
| SQL 来源 | 模型自由生成 | 封闭模板编译 + 参数绑定 |
| 安全 | 依赖提示词 | AST 白名单 + 只读执行 + 限额 |
| 结果可信度 | 模型可能编数字 | 全部确定性计算，逐条证据 |
| 失败处理 | 常静默降级 | 显式状态机，失败关闭 |
| 评测 | 常缺 | 50 题 + 独立标准答案 + 可测试 |
| 交付 | 一个脚本 | CLI + Web + 四份文档 + CI |

## 9. 面试可能问题与参考回答（10 个）

1. **"LLM 只输出计划，会不会太受限？"**
   是取舍：覆盖 9 指标/7 类分析，换来可审计与可回归。扩展方式是加白名单项与模板，而不是放开自由 SQL。

2. **"如何防止提示词注入？"**
   计划 Schema `extra="forbid"`、指标/维度/操作全白名单、用户问题包裹为不可信数据；任何 SQL 字段直接拒绝；执行层再校验一次。

3. **"SQL 安全怎么做的？正则吗？"**
   不是正则。SQLGlot 解析成 AST 后按节点类型/表/函数/列做判定，并做列-表静态绑定；连接层同时关闭外部访问。

4. **"怎么保证数字不是模型编的？"**
   模型不参与计算。数字全部来自 DuckDB 查询 + Python 统计；报告每条结论带 `[E00x]`，与 JSON 证据一一对应。

5. **"LLM 叙述层会不会改数字？"**
   有校验：必须引用证据 ID、数字必须在证据白名单内、禁因果表述；不通过则整段回退确定性文本并在报告注明原因。

6. **"评测怎么避免自证？"**
   标准答案用独立 SQL 与纯 Python 算术生成，且生成期交叉断言；另有 `verify_golden.py` 复算与"篡改即失败"的测试。

7. **"离线 100% 说明什么？"**
   只说明执行链路与独立核算一致，**不说明**真实模型理解能力。真实评测要 `--real` 且有调用预算。

8. **"数据不足/口径冲突怎么处理？"**
   显式状态（`insufficient_data`/`incompatible_metric`），不补零、不猜；页面与报告都展示原因。

9. **"性能如何？"**
   合成数据 50 例端到端 P50≈96ms、P95≈182ms（不含模型延迟）。真实模型场景主要是 API 延迟，本项目未在生产验证。

10. **"隐私呢？"**
    只读、用户级数据仅允许聚合计数、维度列必须 GROUP BY；但**未实现 k-匿名**，细粒度统计仍可能披露——README 与页面都明确提示。
